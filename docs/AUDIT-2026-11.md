# Audit, November 2026

Date: 2026-11-12 · Version: 0.10.0 (`dev`) · Previous review: [Production audit, 29 October 2026](PRODUCTION_AUDIT_2026-10-29.md)

## Scope

A documentation, security-boundary and developer-experience audit of the whole
repository for release 0.10.0. The first pass covered the task-assignment,
design-system and MCP/REST work: the README and docs index, contributor setup,
the task write path (UI, assistant, MCP, REST), design assets and fonts,
supply-chain posture (CI, installer, dependencies) and the unit-test suite. The
second pass is a security review of everything else in the release:
organisation governance and the super-admin console, sign-in, per-workspace
SMTP and notification channels, payments, email campaigns, finance import and
exports, makerspace operations and observability. It is not a penetration test
and it does not re-run the production hosting smoke suite.

## Architecture at a glance

- **Web and API**: Next.js 16 App Router. `proxy.ts` rate-limits, sets CSP
  nonces and passes the path (`x-sw-path`) to the module gate; pages, Server
  Actions and route handlers authenticate and authorise (`requireWorkspace`,
  `getWorkspaceForAction`). Business rules live in `lib/`.
- **Organisations**: each workspace is an organisation with a status
  (PENDING, ACTIVE, REJECTED, SUSPENDED), feature modules (`lib/modules.ts`) and
  limits (`lib/limits`). The instance super admin has audited silent access
  through a synthetic OWNER membership, never a stored row.
- **Data**: PostgreSQL 16 through Prisma, one tenant per workspace, roles
  OWNER, ADMIN, MEMBER and GUEST, private teams for narrower visibility.
- **Background work**: BullMQ on Redis 7. A worker handles email, notifications,
  campaign sending, syncs and monitor checks; beat schedules recurring jobs.
- **Files and secrets**: private S3-compatible storage (Silo or an external
  bucket); application secrets use envelope encryption under a rotatable root key.
- **Machine access**: the in-app assistant, an MCP server at `/api/mcp` and a
  REST API at `/api/v1`, all calling the same task service in `lib/tasks`.
- **Public endpoints**: campaign sign-up, confirmation, tracking and bounce
  webhooks (`/api/public/campaigns/**`), payment webhooks (`/api/payments/**`)
  and Prometheus metrics (`/api/metrics`). Link tokens are stored as hashes,
  webhooks are verified by signature or secret, and `/api/metrics` needs a
  bearer token.
- **Hosting**: VPS with Docker Compose and Caddy, Kubernetes (Helm), Render, AWS,
  DigitalOcean, or a split layout with the frontend on Netlify.
- **Design**: Design-Kit submodule, generated token CSS committed.

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full contract.

### Accepted limits

- Storage, API-token and webhook limits are checked without the workspace lock,
  so a burst of parallel creates can go slightly over the cap. Seat and project
  limits are locked. See [org-governance](areas/org-governance.md#known-limits).
- The campaign worker is at-least-once: a crash after the SMTP server accepted a
  message can send it again. See [email-campaigns](areas/email-campaigns.md).
- Sign in with Apple needs an HTTPS domain.
- Live Stripe, Razorpay and other provider calls are covered by mocked tests only.
- Campaign test sends are not counted in the monthly email cap; they have their
  own daily recipient budget.

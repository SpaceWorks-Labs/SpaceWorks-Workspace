# Application secrets

Secrets lives at `/w/:workspaceSlug/secrets`, separately from the team password Vault. Projects contain ordered environments (dev, staging, production by default) and exact folder paths. Key names follow `[A-Z_][A-Z0-9_]{0,127}`. Each key has a comment, tags, active-member owner and optional rotation interval. The comparison grid displays presence/missing for environments the reader may list, with per-cell reveal only where they may read values. Empty states use Patch; forms use shared accessible controls and stack on narrow screens.

## Security boundary

New ApplicationSecret values and versions use the shared Vault hierarchy: a versioned environment root wraps a workspace key, which wraps a project data key. AES-256-GCM uses a fresh per-value nonce; workspace/project/environment/path/key are authenticated additional data. The same workspace key wraps a dedicated Vault data key. Legacy envelopes remain readable using all configured root versions and migrate on write or during rotation. Snapshots and pending change payloads are separately envelope encrypted. Keep that master key with protected backups; there is no recovery without it. Encryption is server-managed, not end-to-end. The server decrypts only for an authorised read, import comparison or authorised change/restore. Empty values are supported through a non-empty encrypted JSON wrapper (see encryption adapter).

Services recheck active membership, enabled users and unarchived workspace state. Compound tenant references protect project/environment/key ownership. Workspace admins retain administration. Other members need project or environment grants: None, Keys, Read, Write, Admin. Exact environment grants override project grants, including explicit None. Production ignores inherited project grants; it requires an explicit environment grant. Once an environment is marked production, renaming cannot remove that classification.

Fresh Vault MFA (five minutes) is required for production reveals, version reveals, sharing and every user export. CLI proofs are session-bound and checked against current MFA enrolment. Service tokens are intentionally non-interactive capabilities; their creation for production requires the admin's fresh MFA. Reveals/export use POST and no-store browser responses; machine GET responses are also no-store. Plaintext never enters page DTOs, audit, search, activity, notifications, background jobs or assistant/MCP tools. Generic assistant API tokens are rejected by the Secrets endpoints. No application secret values are added to assistant tooling or workspace bundle exports.

Search indexes project and key/environment names only, with PRIVATE owner metadata and a live source access predicate. Revocation immediately hides stale index rows. Global search is deliberately owner/admin scoped in addition to the environment permission check; the Secrets screen lists the full set allowed by grants. Comments and tags never enter search. General activity gets no secret events.

## Changes, references and recovery

`${KEY}` references the same environment/folder; `${staging.KEY}` references another environment root; `${production.api.KEY}` references `/api` in production in the same project. Every target requires read permission and appropriate production MFA. Machine references remain inside the exact token environment and path. Missing/inaccessible references fail the read rather than returning a partial export. Resolved targets are memoized within each read. Cycles, excessive depth (32 levels), resolved values above 200,000 characters, or a total expansion budget above 10,000 target visits or 1,000,000 generated characters per read fail with safe errors.

Each change records an immutable encrypted version, actor and time. Every change set creates an automatic environment snapshot, including an initial empty snapshot before the first write; manual named snapshots are supported. Diffs expose names and add/update/delete/unchanged only. Restoring a version or entire snapshot creates a new change, preserving history. Snapshot recovery applies the complete set, including deletions, atomically without the 500-key import limit; protected-environment approvals and revision checks still apply. Snapshot and per-key history pages have tenant-validated cursors for older records; the display limits do not hide retained recovery points. Deletions are soft so history remains recoverable. If a historical owner has left, recovery preserves an active current owner or assigns the restoring member; environment grants are never changed. Encrypted versions/snapshots are retained until workspace deletion; provision storage and use normal protected database backups. No silent pruning compromises point-in-time recovery.

Protected environments submit `SECRET_CHANGE` through the existing approvals engine. The inbox names the project and environment and links directly to the change diff. An independent workspace admin approves. The hook rechecks the requester's live write permission and the environment revision, then applies the entire encrypted change set transactionally. Stale approvals cannot overwrite newer changes; prepare a new request instead. Rejected/cancelled requests never apply. Production is protected by default; environment admins can configure protection explicitly.

Import accepts pasted text or a browser-selected/dropped `.env` file. File bytes are read in the browser and handled as pasted input, not retained as plaintext attachments. The bounded parser supports comments, BOM/CRLF, export prefixes, quoted multiline values and double-quote escapes. It rejects duplicate/invalid keys, nulls, more than 500 keys and input above 200 KB. Preview shows add/update/unchanged; applying revalidates the original input and revision. No unencrypted file enters object storage. Explicit exports resolve references and produce env/JSON/YAML. This area has no monetary or proof records requiring receipt attachments.

## Machines, CLI and shares

Service tokens are exact project/environment/path capabilities, read-only by default, with optional expiry and IP/CIDR allowlists. Only the hash is stored; the token is shown once. Every authenticated token use is audited; creator membership, current environment access, expiry, revocation and scope are checked on every request. IP addresses come from the existing trusted-proxy helper; an unknown IP cannot satisfy an allowlist. Per-IP and per-token rate limits use existing Redis fail-closed buckets. Writable tokens still cannot bypass approvals or manage grants, snapshots or service tokens.

`GET /api/v1/secrets?project=ID&environment=dev&path=/&format=env|json|yaml` exports; `list=true` returns keys only and `key=NAME` reveals one key. POST accepts `{ project, environment, changes: [{ key, path, value }] }`; `{ delete:true }` removes a key. Device login endpoints live under `/api/cli/device/{code,token}`; refresh, own-session list/revoke, whoami and session MFA endpoints live under `/api/cli`. HTTPS is required outside localhost. Device codes expire in ten minutes, poll every five seconds, are hashed, row-locked and consumed once. Approval requires a signed-in enabled user and MFA when enrolled. Access tokens last 15 minutes; refresh credentials rotate and expire after 30 days. All comparisons use constant-time hash checks. Account → CLI devices revokes sessions immediately.

The Node 20+ workspace package `@spaceworks-labs/workspace-cli` (single runtime dependency: `cross-spawn`, for Windows command shims in `sww run`) supplies `sww login/init/secrets/run/export/whoami/logout/tokens` and the `getSecrets` SDK. See [package quickstart](../../packages/cli/README.md). `.sww.json` holds no secrets. Credentials use the OS keychain where available or a 0600 file in a 0700 directory. `run` injects values without writing files and forwards child signals/exit codes. The SDK's optional bounded cache defaults off; only calls with a positive `cacheTtlMs` read or populate it.

Sharing encrypts text in the browser with AES-256-GCM. The server stores ciphertext plus a hashed capability; the 256-bit decryption key remains solely in the URL fragment. `/share` removes the fragment from browser history, transmits only the capability on an explicit view, and decrypts locally. Consumption is row-locked; one-time links disappear on the first view and limited links on the last. Expired rows are deleted by the scheduled job, including in archived workspaces. There is no GET consumption or prefetch. Text hides after 30 seconds or tab hiding. Hiding the tab during fetch/decryption discards the pending reveal even if the tab becomes visible again; the consumed share stays hidden. This is bearer sharing; send the whole link only to the intended recipient.

## Operations and integration

`lib/scheduled/secrets.ts` is registered in the BullMQ registry. It removes expired device/share capabilities and dispatches daily deduplicated owner rotation reminders with generic text and ids only. Reminders recheck the owner's access. Security views report overdue rotations, tokens without expiry, unused tokens, production access holders and recent reveals. Project audit CSV is scoped to environments the caller administers; action/date filters never include values. The screen shows the latest 300 environment events. CSV refuses results above 10,000 rows and asks for a narrower date range, so exports never silently omit history.

Demo module `scripts/seed/secrets.mjs` adds a fictional Website project, three environments, ten keys per environment, encrypted starting snapshots, one discarded-plaintext service token and a pending production approval. Create a fresh token in the UI for actual use. No external connectors or sync integrations are supplied.

No deployment/release/root README changes are needed. All new tenant tables cascade on workspace deletion; global device/session rows are authentication records with user-session cascade.

## Machine identities and universal authentication

Machine identities are the recommended application/CI capability. Workspace admins create a project identity, then grant exact environment/path permissions (None, Keys, Read, Write). An identity can have several client secrets, each displayed once and stored as SHA-256 hashes. `clientId` is public metadata. Existing static service tokens remain supported and are labelled legacy. Creator membership must remain active and enabled; archived workspaces and revoked identities cannot authenticate.

`POST /api/v1/auth/universal/login` accepts `{clientId, clientSecret}` and returns `{accessToken, expiresIn, tokenType}` with no-store headers. Access tokens are hashed, expire after two hours by default, and have a thirty-day maximum renewable lifetime. `POST /api/v1/auth/universal/renew` takes the bearer token, rotates it and preserves its original maximum lifetime and remaining uses. `POST /api/v1/auth/universal/revoke` revokes the supplied access token; CLI logout uses it before clearing the local keyring. Login and token-use CIDR policies are separate; unknown IPs cannot satisfy a non-empty policy. Finite client-secret uses count successful logins; finite access-token uses include renewals. Expired client secrets invalidate their access tokens. Three failures lock an identity for five minutes by default; admins can edit the settings and reset lockout. Saving settings revokes existing access tokens; client-secret limits apply when issuing new secrets. Revoking an identity, client secret or access token takes effect on the next request. Counters, lockout and renewal claims are transaction-locked. Every authenticated use, management operation and known-identity login failure is audited, with Redis fail-closed request limits. Production grants and credential administration require fresh MFA.

CLI aliases: `--domain` / `SWW_DOMAIN`, `--projectId`, `--env`, `--path`. Old `--host` / `--project` and existing config fields remain compatible. `sww login` prompts for the URL when interactive, remembers the signed-in instance, and opens the device flow; `-i` prints the URL/code without opening a browser. `sww login status` reports local credential status. `sww login --method=universal-auth --client-id ID --client-secret SECRET --plain --silent` emits only the access token for `SWW_TOKEN`. Plain CI login does not persist the token. `sww init` writes `projectId`, `defaultEnvironment`, `path`, `domain` to `.sww.json`. `dotenv` is accepted alongside `env`, JSON and YAML. Device logout refreshes the stored session before revoking it, so expired access tokens do not leave refresh credentials live. Logout clears local credentials even if refresh or remote revocation fails. Credentials remain in the OS keyring or the existing private-file fallback.

## Local scanning

`sww scan` scans tracked/untracked non-ignored working files; `--staged` reads the index, and `--history` reads all reachable revisions. Detectors cover AWS, GitHub, Slack, Stripe, Google, private-key headers, JWTs and high-entropy credential assignments. Findings contain filename, line, detector and SHA-256 fingerprint, never matched values. Review false positives and add `fingerprint:HASH` or path globs to `.swwignore`. Binary files and standard build/dependency directories are skipped. Oversized files fail visibly rather than silently passing. `sww scan install --pre-commit` prepends the staged check to an existing shell hook without overwriting its body; hooks with unsupported interpreters are refused without modifying the file. A finding exits with status 1. Scanning is heuristic, local and has no network integration.

## Encryption operations

Encryption settings expose only versions, fingerprints, algorithm, dates and the last job status/progress. Key bytes and wrapped key material never enter page DTOs, API responses, exports, CLI, search, activity or jobs. Both project and workspace rotation require a workspace admin and fresh Vault MFA. Rotation has a durable SQL record, a BullMQ one-off job and scheduled recovery if enqueueing fails. Each batch and cursor commit together; previous versions stay decrypt-only. Project rotation re-encrypts values, retained versions, snapshot contents and pending approval payloads. Workspace rotation re-wraps all child key versions and migrates legacy Vault items/versions, plus the selected project's legacy records. Rotate each remaining project before retiring roots that protect legacy envelopes. A failed batch retains its cursor and resumes on retry; the UI continues to display the running job.

Configure `VAULT_MASTER_KEYS="2:BASE64_NEW,1:BASE64_OLD"` on web and worker; the first entry encrypts and all versions decrypt. `VAULT_MASTER_KEY` alone remains version 1. Never remove the old root during migration or while protected historical backups still depend on it. Inside the backend image, whose existing scripts wildcard includes both the operator command and its shared JavaScript crypto helper, run `node --env-file-if-exists=.env scripts/rotate-root-key.mjs` (or inject environment variables and run `node scripts/rotate-root-key.mjs`). It transactionally re-wraps workspace keys with the newest root, is safe to resume and reports remaining legacy envelopes without printing key material. No deployment-file changes are required. The `InternalKeyProvider` interface in `lib/vault/hierarchy.ts` is a server-only wrapping seam for a future external KMS provider. No external provider is implemented.

Values stay masked with eight fixed dots until explicit reveal/copy. Reveals and version diffs hide after at most sixty seconds, on tab/window blur and on navigation; stale in-flight reveals are discarded. Copy fetches and audits separately without revealing onscreen, then conditionally clears the clipboard after thirty seconds if browser permissions allow. Production reveal/copy/version access retains the stricter existing five-minute MFA window. Metadata lists never fetch values. Opening the metadata editor does not fetch the stored value; its explicit show control fetches and audits the value before saving is enabled. A multiline editor has a show/hide control, and version comparison reveals both authorised versions only on demand.

## Google Meet follow-up

After a conference create/update, the request checks the event up to five times with short capped backoff and per-read timeouts. Pending creation is persisted on the sync binding and meeting; an immediate BullMQ job retries it, with scheduled recovery and a one-hour terminal limit. Jobs carry only the binding id and recheck active membership, organiser authority, connection and tenant. Only HTTPS Google Meet URLs are accepted. The meeting page and calendar popover show pending text and refresh while pending, then display the link and Join action. Updated invitation HTML, text and ICS include the link. Provider calls are mocked in tests. See [Google conference resource](https://developers.google.com/workspace/calendar/api/v3/reference/events) and [conferenceDataVersion](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert).

Additional shared edits: `lib/crypto.ts`, `lib/vault/service.ts`, `lib/env.ts` for shared hierarchy and root-list validation; queue definitions/worker for ID-only rotation and Meet jobs; calendar Google sync, scheduled recovery, invitation emails, meeting page and popover for Meet readiness. Migration `20261021016000_secrets_identities` adds identity/key/job records and the small pending-link fields. No external connectors, monetary records or new file-storage paths are introduced.
